RAG & Retrieval

RAG Is Not the Hard Part

By Tharun Kumar ReddySep 20265 min read

Most teams treat RAG as the hard problem: which vector database, what chunk size, which embedding model. In practice, standing up a retrieval pipeline that returns plausible-looking answers is the easy part — maybe 20% of the work. The other 80% is what happens after retrieval: grounding, citations, deciding when to say nothing at all, and staying fast enough that someone actually uses it in the flow of their work instead of falling back to Ctrl+F.

The retrieval pipeline is a commodity now

LangChain or LlamaIndex for orchestration, ChromaDB or pgvector or Qdrant for storage, OpenAI or Azure OpenAI for embeddings — these pieces are reasonably interchangeable, and a basic pipeline can be stood up in a day. That's not a criticism; it's just no longer where the differentiation lives. If your RAG project's hardest technical decision was "which vector DB," you haven't hit the actual hard part yet.

Grounding and abstention are the actual product

A system that confidently answers even when retrieval quality is poor erodes trust fast, especially once its output starts feeding real operational decisions. Citation-grounded generation and explicit abstention on low-relevance retrieval aren't nice-to-haves bolted on at the end — they're the part of the system that determines whether anyone keeps using it after the first bad answer.

A RAG demo answers one kind of question. A RAG system in production has to know which kind of question it's being asked.

Multi-source retrieval is where tutorials stop

Combining structured data (a SQL query against Postgres or MySQL) with unstructured retrieval (documents, OCR'd text, vector search) in the same query path is where most walkthroughs end and most real systems begin. Intent routing — deciding whether a question needs an exact number from a database or a synthesized answer from documents — is unglamorous, and it's also the difference between a toy and a tool.

Where this leaves me

I come at this from the data engineering side, and the parts of RAG I find most interesting aren't the model calls — they're the same discipline data engineering has always demanded: idempotent processing, cost control on re-embedding, and building a system that knows the limits of what it actually knows.
